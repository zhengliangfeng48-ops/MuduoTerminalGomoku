- 时间：20261018-155800
- 工具：`benchmarks/scale_test.py`（Python 标准库，selector 驱动；脚本自动拉起服务端并抬高 ulimit）
- 服务端：`gomoku_server --io-threads 4 --port 9527 --http-port 8080`
- 环境：13th Gen Intel(R) Core(TM) i5-13500H / 16 核 / 7810 MB / WSL2 Ubuntu 22.04（内核 6.6.114.1）
- 说明：所有连接都**完成 REGISTER/LOGIN 认证**后才计入；在线数通过服务端 `/stats` 的 `online` 字段交叉校验。

## 4. 分析

1. **连接能力不是瓶颈**：20000 并发连接全部建立并认证成功，服务端 CPU 与内存均有余量；
   真正限制来自 `ulimit -n`（服务端与压测端都改为 65535 后才跑得动）。
2. **认证吞吐才是瓶颈**：约 210-250 次/秒。原因很明确——服务端只用**一条** MySQL 连接
   （`Db` 用 mutex 串行化），且每次注册/登录都是一次独立事务，InnoDB 默认
   `innodb_flush_log_at_trx_commit=1` 会 fsync。所以"上人速度"受 DB 限制，
   与网络层无关；小规模对局场景完全够用。
3. **单连接 RTT 约 0.05 ms**：说明 muduo 的 epoll 读写路径 + 我们的文本协议解析在几十微秒量级。
4. **延迟随并发线性增长**：100/500/1000 连接时 p50 为 1.4 / 9.7 / 21.5 ms，
   总吞吐稳定在 4.5-5.5 万 req/s，符合"单连接一次只有一个未完成请求"的闭环特征。
5. **CHAT 广播比 PING 慢**：因为一条聊天要 fan-out 给同房间所有成员（4 个房间各 12/50 人），
   200 连接时 p50 已到 16 ms、p99 82 ms。
6. c=100 的 PING 用例出现过一个 2427 ms 的离群点（首轮建连/系统调度抖动），
   p99 只有 2.2 ms，看尾部延迟应以 p99 为准。
